# Progressive Web App — Offline, Install & Background Sync (M10)

The **citizen app** (`frontend/citizen-pwa`) is an installable, offline-capable PWA. The
**officer portal** (`frontend/admin-portal`) is intentionally **not** a PWA — it only gains
connectivity detection (a banner). No business module or existing complaint API changed;
the only backend addition is idempotency, which is opt-in via a request header and fully
backward compatible.

## PWA architecture

| Concern          | Implementation                                                                   |
| ---------------- | -------------------------------------------------------------------------------- |
| Build/SW tooling | `vite-plugin-pwa` (Workbox `generateSW`)                                         |
| Registration     | `virtual:pwa-register/react` → `PwaReloadPrompt`                                 |
| Manifest         | Generated by the plugin (`dist/manifest.webmanifest`)                            |
| Icons            | `scripts/gen-icons.mjs` emits regular + maskable PNGs (192/512) + Apple touch    |
| Install          | `useInstallPrompt` (captures `beforeinstallprompt`) → `InstallPrompt` card       |
| Update flow      | `registerType: 'prompt'` → toast with **Reload** action                          |
| Offline UX       | `OfflineBanner` (citizen), `Offline` fallback page, `ConnectivityBanner` (admin) |
| Offline queue    | IndexedDB (`offline-queue.js`) + `useOfflineComplaintSync`                       |
| Idempotency      | `Idempotency-Key` header + backend replay middleware                             |

## Service-worker architecture

`generateSW` precaches the app shell (hashed JS/CSS/HTML/icons) and applies runtime caching
per request type. SPA navigations fall back to the precached `index.html`, so the app opens
offline. `navigateFallbackDenylist` excludes `/api/**` so API calls never resolve to HTML.

## Cache strategy

| Bucket                     | Matches                                 | Strategy                      | Rationale                       |
| -------------------------- | --------------------------------------- | ----------------------------- | ------------------------------- |
| `dgp-app-shell` (precache) | built JS/CSS/HTML/icons                 | Precache (CacheFirst)         | Instant, offline-first shell    |
| `dgp-static-assets`        | `script` / `style` requests             | StaleWhileRevalidate          | Fast, refreshed in background   |
| `dgp-images`               | `image` requests                        | CacheFirst (30d, 80 entries)  | Rarely change                   |
| `dgp-api`                  | `/api/v1/{notices,schemes,tax,auth/me}` | NetworkFirst (4s timeout, 1d) | Fresh online, last-good offline |

Read-offline coverage required by the blueprint — **Notices, Schemes, Tax, Profile
(`auth/me`)** — is served by the `dgp-api` NetworkFirst bucket. **Complaint history** and
detail render from the same cached shell + TanStack Query cache.

## Offline queue architecture

When a complaint is submitted while `navigator.onLine` is false (or the request fails with
no server response), it is stored in IndexedDB with a unique `Idempotency-Key`. On the next
`online` event (and once on mount) `useOfflineComplaintSync` drains the queue in submission
order:

1. Replay each item via `complaintService.create(payload, idempotencyKey)`.
2. On success → remove from queue.
3. On a **server** response (2xx or 4xx) → remove from queue (delivered or permanently
   rejected — never loop on a poison record).
4. On a **network** error → stop and keep the rest for the next reconnect.

Because every replay carries the same key, an item delivered but not yet dequeued (e.g. the
tab closed mid-sync) is collapsed by the backend rather than duplicated.

### IndexedDB schema

- **Database:** `dgp-offline` (version 1)
- **Object store:** `complaint-queue`, `keyPath: 'id'`
- **Record:** `{ id, idempotencyKey, payload: { category, title, description, address?, latitude?, longitude?, accuracy?, images: File[] }, createdAt }`
  - `id === idempotencyKey` (unique), so re-queuing the same attempt is a no-op upsert.

## Idempotency implementation

- **Model:** `IdempotencyKey` (`backend/src/features/idempotency/idempotency.model.js`) —
  unique `key`, stored `statusCode` + `response`, TTL index expiring records after 24h.
- **Middleware:** `idempotency` (`backend/src/middlewares/idempotency.middleware.js`):
  - No `Idempotency-Key` header → pure pass-through (every existing endpoint unchanged).
  - Known key → replay stored status + body (no duplicate side-effect).
  - New key → reserve immediately (blocks concurrent duplicates), then capture the 2xx
    response; on a non-2xx the reservation is dropped so the client can retry cleanly.
- **Wiring:** inserted into `POST /api/v1/complaints` after auth, before upload/validate.
  No other route is affected.

## Localization

All new UI strings are keyed under `pwa.*`, `settings.*`, `onboarding.*` (citizen) and
`conn.*` (admin), fully translated in **EN + MR** with verified key parity (261 keys citizen,
401 keys admin — no missing keys, no hardcoded strings).

## Settings & onboarding

`Settings` hub (`/settings`): Language, Appearance (theme), Notification preferences,
Help & FAQ (accordion), and **Replay onboarding**. The three-slide onboarding intro shows
once on first launch (persisted in `localStorage`) and re-opens via a window event when
replayed from Settings.

## Performance

- **Route-level code splitting:** every screen is `React.lazy` + `Suspense`; Leaflet, forms
  and other heavy deps load on demand.
- **Vendor chunks:** `manualChunks` splits `react-vendor`, `query`, `motion`, `leaflet`,
  `i18n`. The 500 kB bundle-size warning is resolved — the largest chunk is ~227 kB and
  route chunks are a few kB each.

## Admin portal

Not a PWA. `ConnectivityBanner` shows a persistent warning while offline and a brief "Back
online" confirmation on reconnect. No service worker, no caching, no offline data.
